# FoodScope Horizon 食品行业版设计

## 1. 产品目标

FoodScope 第一期以开源项目 Horizon 为技术基座，交付一套可定时运行的全球食品产业情报流水线。系统面向中国食品企业的产品与研发人员，持续采集美国、欧盟、英国、日本、韩国及部分东南亚市场的信息，自动完成中文翻译、去重、行业分类、摘要、重要性评分、合规风险识别和商业机会分析，并生成一份结构稳定的中文每日综合简报。

一期是 Horizon 的食品行业版，不是完整资讯平台。它不包含公开网站、外部数据库、用户账号、付费、多租户、站内搜索、收藏或编辑后台。

## 2. 成功标准

- 每天北京时间 06:30 自动抓取过去 30 小时内容，07:30 前完成简报生成与分发。
- 首批接入约 40 个直连来源和约 20 组多语言发现查询。
- 每日综合简报通常收录 15–25 条有效情报，“今日必读”不超过 5 条。
- Markdown、HTML、邮件、飞书和微信公众号草稿使用同一份内容事实版本。
- 任一来源、单条内容、单个 AI 请求或单个分发渠道失败，不阻断其他内容和渠道。
- 生产运行连续 14 天，至少 95% 的计划任务按时完成；失败运行可从最近成功阶段恢复。
- 抽样验收中，入报内容食品行业相关率不低于 90%，重复事件率不高于 5%，原文链接有效率不低于 98%。

## 3. 技术形态

### 3.1 Horizon 基线

- 以 Thysrael/Horizon 主线代码为初始基线，保留 MIT 版权声明、许可证和上游来源说明。
- 维持 Python 3.11、`uv`、Docker、CLI、pytest、Pydantic、异步抓取和现有 MCP 架构。
- FoodScope 的行业模型、来源适配器、提示词、输出模板和渠道适配均在同一代码库中维护；记录导入时的上游提交，后续通过独立 `upstream` remote 评估合并。

### 3.2 单应用与文件状态

- 一期运行一个 Docker 应用，不建设 Web/API 服务和外部数据库。
- 生产环境默认部署在香港或新加坡 Linux 主机，以 Docker Compose 和持久化数据卷运行；GitHub Actions 用于测试、手动补跑和备用定时任务。
- 运行产物按 `data/runs/{run_id}/` 保存，阶段固定为：
  `raw → normalized → scored → filtered → enriched → summary`。
- 每个阶段保存 JSON 产物和元数据；失败后可从上一成功阶段继续，避免重复抓取和重复模型费用。
- `data/state/` 保存来源游标、最近运行、规范化 URL 指纹、事件指纹、分发记录和 7 天跨日去重窗口。
- 原始正文和阶段产物保留 30 天；简报、运行元数据和分发记录保留 180 天。

### 3.3 配置与秘密

- `data/config.json` 保存非秘密配置，并支持 `${ENV_NAME}` 环境变量替换。
- AI、SMTP、飞书和微信公众号凭证只从环境变量读取。
- AI 配置拆成 `fast` 与 `analysis` 两个路由；两者分别配置 provider、model、base URL、API key 环境变量、并发、超时和重试，不内置必须使用的供应商。
- 未配置必要凭证时，配置校验应明确指出缺失项；禁用某渠道时不要求该渠道凭证。

## 4. 来源与采集

### 4.1 来源等级

- 一级：监管机构、标准组织、政府数据接口及原始企业公告。
- 二级：可信食品、配料、包装、零售餐饮行业媒体，研究机构和企业新闻中心。
- 三级：Google News、GDELT 等关键词发现结果，只用于补充线索。

三级内容只有在找到原始出处，或得到至少两个独立可信来源交叉验证后，才允许进入简报。法规、标准、召回和安全事件必须回链一级官方来源。

### 4.2 首批区域

- 美国：FDA 食品 RSS、召回 XML/页面、USDA FSIS 召回与公告。
- 欧盟：欧委会 Food Safety、EFSA、RASFF、EUR-Lex 食品相关更新。
- 英国：FSA Food Alerts API、法规与行业公告。
- 日本：消费者厅食品标签与召回、厚生劳动省食品安全、农林水产省相关公告。
- 韩国：MFDS/进口食品信息、Food Safety Korea 公告和召回。
- 全球组织：Codex、FAO、WHO/INFOSAN 的食品标准与安全更新。
- 东南亚首批：新加坡 SFA RSS 与公告；马来西亚、泰国和越南以权威网页监测及英文发现查询补充。
- 二级行业来源覆盖新品、配料与工艺、包装、消费研究、零售餐饮和重点食品企业动态。

### 4.3 发现查询

约 20 组查询是可配置的主题与语言组合，不是固定网站列表。首批覆盖：

- 新品与饮料创新；
- 新原料、食品添加剂、发酵、生物技术和加工工艺；
- 可持续、可回收、智能包装与标签技术；
- 健康、功能性、减糖、植物基和替代蛋白；
- 消费趋势、零售和餐饮新品；
- 食品法规、标签规则、添加剂标准和进口要求；
- 召回、过敏原、微生物、污染物和食品欺诈；
- 重点企业、品牌和零售商动态。

每组按英语、日语、韩语或目标市场关键词配置。查询结果进入候选池后再执行时间、来源、相关性、证据和重复性校验。

## 5. 食品情报模型与 AI 流水线

### 5.1 内容字段

统一内容对象在 Horizon `ContentItem` 基础上增加：

- 市场与国家；
- 主分类与多值标签；
- 食品品类、原料/技术、品牌/企业；
- 来源等级与原始语言；
- 原文标题、中文标题和中文摘要；
- 重要性分数、风险等级、机会分数；
- 研发意义、风险信号、机会信号、建议关注动作；
- 原始出处、补充证据链接；
- 模型、提示词和分析 Schema 版本。

### 5.2 固定分类

主分类只能选择一个：

1. 产品创新
2. 原料与技术
3. 包装与标签
4. 消费趋势
5. 法规与标准
6. 食品安全与召回
7. 零售餐饮
8. 企业动态

内容可同时具有多个市场、品类、原料、企业和风险标签。

### 5.3 处理步骤

1. 并发抓取来源，保存原始响应和正文。
2. 标准化时间、URL、来源、语言和基础元数据。
3. 快速模型翻译标题与摘要，执行食品相关性判断、分类和实体抽取。
4. 规范化 URL 去重；以中文化标题、企业、产品和事件生成 7 天事件指纹；同次运行再由分析模型合并跨语言同事件。
5. 重要性按 0–10 分评估新颖性、研发相关性、市场影响、可行动性、证据质量和时效性。
6. 独立生成风险等级（无、低、中、高、严重）和机会分数（0–10），不将风险等同于重要性。
7. 分数和分类配额过滤后，分析模型生成研发意义、潜在风险、可借鉴方向和建议关注动作。
8. 生成统一内容模型，再渲染各渠道格式。

所有模型输出必须通过 Pydantic Schema 校验。单条最多重试三次，仍失败则进入隔离清单且不进入简报。模型不得生成无来源的具体法规条文、日期、限量或处罚结论。

### 5.4 自动入报规则

- 全流程不设置人工审批。
- 一级和二级来源通过最低分数、时间与重复校验后可自动入报。
- 三级来源必须满足原始出处或双来源验证规则。
- 法规、标准、召回和安全内容必须具有官方证据链接。
- 失败、缺正文、日期不可判定、Schema 不合格或证据不足的内容进入隔离清单。
- 简报明确标注 AI 生成与“仅供行业研究参考，不构成法律或合规意见”。

## 6. 简报与分发

### 6.1 综合日报

简报固定结构：

1. 标题、日期、覆盖时间窗和运行统计；
2. 今日必读，最多 5 条；
3. 八个行业分类章节；
4. 今日研发启示与值得持续观察的信号；
5. 来源与 AI 声明。

每条情报输出中文标题、原文标题、三句摘要、发生了什么、为何与中国食品研发有关、可借鉴方向、潜在风险、建议动作、市场/分类/标签、来源等级和原文链接。

最终入报 15–25 条。产品创新、原料与技术、包装与标签合计不少于 50%；法规与安全不设置最低配额，避免用低价值内容凑数。

### 6.2 渠道

- Markdown：完整权威归档。
- HTML：由同一 Markdown 渲染，内联样式，供邮件和公众号复用。
- 邮件：使用现有 SMTP/IMAP 订阅能力，发送完整日报并支持退订。
- 飞书：复用并扩展 Horizon Card JSON 2.0 折叠卡片；超长时发送概览加分类卡片。
- 微信公众号：通过公众号 API 写入草稿箱，不在一期自动执行群发；使用配置的永久封面素材，正文保留原文链接和声明。
- MCP：沿用 Horizon 本地 stdio MCP，扩展食品行业阶段字段、运行列表、隔离清单和最新简报资源。通用 Agent 可校验配置、触发流水线、读取各阶段和简报，但不能修改配置、删除产物或直接群发。

各渠道独立重试并记录结果。某个渠道失败不会回滚已生成简报或阻止其他渠道发送。

## 7. 可靠性与安全

- HTTP 抓取设置域名级并发、超时、指数退避、User-Agent 和频率限制。
- 遵守 robots、站点条款和版权边界；简报只保存必要摘要与证据链接，不转载受版权保护的完整文章。
- URL 访问执行 SSRF 防护，拒绝私网、环回、文件协议和重定向到受限地址。
- 日志不得输出 API key、Webhook、邮箱密码或公众号凭证。
- 运行完成时输出抓取数、去重数、入报数、隔离数、模型 token、分渠道结果和总耗时。
- 定时任务设置运行锁，避免同一时间窗重复执行；手动补跑必须显式指定是否重新分发。

## 8. 测试与验收

- 单元测试：配置、来源解析、时间标准化、URL 规范化、跨日指纹、分类配额、Schema 校验、模板渲染和秘密脱敏。
- 契约测试：每个一级专用来源保存脱敏 fixture，验证页面或 API 变更能被检测。
- AI 测试：使用固定中英日韩样本和模拟客户端，覆盖正常 JSON、格式错误、超时、重试和隔离。
- 端到端测试：以本地 fixture 完成全阶段运行，验证 Markdown/HTML、邮件、飞书、微信草稿请求和 MCP 资源一致。
- 故障测试：单源失败、单条解析失败、快速模型失败、分析模型失败、一个分发渠道失败、重复调度和阶段恢复。
- 发布验收：连续 14 天试运行，核对定时完成率、相关率、重复率、原文链接有效率、渠道成功率和模型成本。

## 9. 一期边界与后续

一期不建设长期内容数据库、公开资讯站、站内搜索、用户画像、收藏、个性化订阅、编辑后台、多租户或付费。后续若简报质量和使用频率得到验证，再将同一内容模型迁移到持久化数据库和产品网站；一期文件产物与版本字段应保证未来可导入。
