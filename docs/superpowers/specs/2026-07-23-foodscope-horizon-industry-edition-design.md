# FoodScope Horizon 食品行业版设计

## 1. 产品目标

FoodScope 第一期以开源项目 Horizon 为技术基座，交付一套开源、自部署、配置驱动的全球食品产业情报流水线。系统面向中国食品企业、品牌方及行业从业者，持续采集美国、欧盟、英国、日本、韩国及部分东南亚市场的信息，自动完成中文翻译、跨语言事件去重、行业分类、摘要、重要性评分、合规风险识别和商业机会分析，并按使用者选择的画像生成中文每日简报。

FoodScope 延续 Horizon“配置来源 → 抓取 → 去重 → AI 评分与过滤 → 补充分析 → 生成简报 → 多渠道分发”的核心逻辑。第一期不是完整资讯平台，不建设公开网站、外部数据库、用户账号、付费、多租户、站内搜索、收藏或编辑后台。

项目采用“轻量 Fork + 食品行业扩展”：尽量保留 Horizon 的通用核心、CLI、配置方式、部署方式和分发能力，将食品来源、分类、证据、评分、画像与模板放在边界清晰的行业模块中。

## 2. 成功标准

- 使用者可配置定时启动时间、时区和抓取回溯窗口；默认每天北京时间 06:30 抓取过去 30 小时内容，并以启动后 60 分钟内完成简报生成与分发为目标。
- 程序代码、来源配置、提示词、评分规则和简报模板全部开源；AI 与分发渠道密钥由使用者自行提供，且只从环境变量读取。
- 内置官方证据、全球行业、新品、原料研发、包装加工、零售餐饮、日韩、东南亚、研究数据和 X 弱信号等来源包。来源数量不是硬编码的产品限制，使用者可启停、组合、覆盖或新增来源。
- 内置综合情报、市场行情、新品雷达、产品研发和合规安全五种简报画像。首次运行默认使用综合情报版，商业与技术内容原则上不少于 70%。
- 每次运行默认启用一个简报画像，通常收录 15–25 条有效情报，“今日必读”不超过 5 条。使用者可复制内置画像并调整主题、地区、品类、来源和栏目权重。
- Markdown、HTML、邮件、飞书和微信公众号草稿使用同一份内容事实版本。
- 任一来源、单条内容、单个 AI 请求或单个分发渠道失败，不阻断其他内容和渠道。
- 生产运行连续 14 天，至少 95% 的计划任务按时完成；失败运行可从最近成功阶段恢复。
- 抽样验收中，入报内容食品行业相关率不低于 90%，重复事件率不高于 5%，原文链接有效率不低于 98%。

全部媒体与社交候选见[《行业媒体与商业信号源候选池》](2026-07-23-foodscope-industry-media-longlist.md)，当前暂定入口、采集方式、查询式与降级规则见[《一期来源与发现查询目录》](2026-07-23-foodscope-source-catalog.md)。来源目录需要按本设计重新组织为可组合来源包；候选池保留所有筛选记录作为审计轨迹。

## 3. 技术形态

### 3.1 Horizon 基线与轻量 Fork

- 以 Thysrael/Horizon 主线代码为初始基线，保留 MIT 版权声明、许可证和上游来源说明。
- 维持 Python 3.11、`uv`、Docker、CLI、pytest、Pydantic、异步抓取和现有 MCP 架构。
- 保留 Horizon 的配置读取、通用来源、抓取、URL 去重、AI 路由、简报生成、邮件、Webhook、MCP 和本地文件输出能力。
- 记录导入时的上游提交，保留独立 `upstream` remote，定期评估同步。可通用化的改进优先以兼容方式实现，并适合时向 Horizon 上游贡献。
- 核心只增加必要的通用扩展接口，例如行业标准化器、分类器、事件去重器、证据校验器、评分器和简报渲染器。食品规则不得散落在 Horizon 通用模块中。

### 3.2 食品行业扩展边界

食品行业能力按单一职责拆分：

- `food_sources`：官方、媒体、发现查询和区域来源包及专用适配器；
- `food_taxonomy`：食品主分类、市场、品类、原料、技术、企业与风险标签；
- `food_evidence`：原始出处、交叉验证和法规、安全、召回的证据准入；
- `food_analysis`：重要性、画像相关性、商业机会、风险和证据质量分析；
- `food_profiles`：综合、市场、新品、研发和合规画像；
- `food_templates`：食品行业 Markdown、HTML、邮件、飞书和微信公众号模板。

概念数据流为：

`Horizon 读取配置并抓取 → FoodScope 标准化、分类和跨语言事件去重 → FoodScope 执行证据与多维评分 → 按画像选择内容 → Horizon 生成并分发`

单个行业扩展处理失败时只隔离该条内容，不得令整次运行崩溃。

### 3.3 单应用与文件状态

- 一期运行一个 Docker 应用，不建设 Web/API 服务和外部数据库。
- 生产环境默认部署在香港或新加坡 Linux 主机，以 Docker Compose 和持久化数据卷运行；GitHub Actions 用于测试、手动补跑和备用定时任务。
- 运行产物按 `data/runs/{run_id}/` 保存，阶段固定为：
  `raw → normalized → scored → filtered → enriched → summary`。
- 每个阶段保存 JSON 产物和元数据；失败后可从上一成功阶段继续，避免重复抓取和重复模型费用。
- `data/state/` 保存来源游标、最近运行、规范化 URL 指纹、事件指纹、分发记录和 7 天跨日去重窗口。
- 原始正文和阶段产物保留 30 天；简报、运行元数据和分发记录保留 180 天。
- 默认按北京时间 06:30 抓取过去 30 小时，但时区、Cron 表达式、回溯时长和目标交付时长均由使用者配置。

### 3.4 配置与秘密

- `data/config.json` 是非秘密配置的唯一权威来源，并支持 `${ENV_NAME}` 环境变量替换。
- 初始化向导生成同一份 JSON 配置，不维护独立状态；没有向导时也可完整手动配置。
- `schedule.timezone`、`schedule.cron`、`collection.lookback_hours` 和 `delivery.target_minutes` 分别控制运行时区、定时表达式、默认回溯时长和目标交付时长；默认值依次为 `Asia/Shanghai`、`30 6 * * *`、`30` 和 `60`。
- 手动运行支持 `--hours` 或 `--since`/`--until` 临时覆盖抓取时间窗，不修改持久配置；`--no-deliver` 可用于只生成简报的补跑。
- AI、SMTP、飞书和微信公众号凭证只从环境变量读取。
- AI 配置拆成 `fast` 与 `analysis` 两个路由；两者分别配置 provider、model、base URL、API key 环境变量、并发、超时和重试，不内置必须使用的供应商。
- 运行前校验来源包、简报画像、主题权重、栏目上限、AI 路由和必要凭证。禁用某渠道时不要求该渠道凭证；错误必须指出具体字段和修复方向。

## 4. 来源与采集

### 4.1 来源证据等级

- 一级：监管机构、标准组织、政府数据接口及相关事件的原始企业公告。
- 二级：可信食品、配料、包装、零售餐饮行业媒体，研究机构和企业新闻中心。
- 三级：Google News、GDELT 等关键词发现结果，只用于补充线索。
- 四级：X 等社交平台中的机构、媒体、企业和专家账号，只用于发现早期弱信号。

三级内容只有在找到原始出处，或得到至少两个独立可信来源交叉验证后，才允许进入简报。四级内容不能直接进入简报，必须先回链至可独立核验的原始出处，再按该出处的实际等级重新评估。点赞、转发、评论量和单个匿名个案不能单独支撑趋势判断。

法规、标准、召回和食品安全结论必须回链政府、监管机构或标准组织的官方证据。企业新品可以把品牌或企业的原始产品页、公告作为一手出处，但供应商自述不能单独支撑法规、市场规模或技术效果结论。

### 4.2 来源包

来源包决定“系统去哪里找信息”，简报画像决定“从候选池中选择什么”，两者相互独立。内置来源包包括：

- `official_evidence`：法规、标准、召回和食品安全的官方证据入口；
- `global_industry`：全球综合食品行业媒体；
- `product_launches`：食品饮料新品、品牌上新、自有品牌、餐饮菜单新品和限定产品；
- `ingredients_rd`：配料、营养、食品科学、配方和研发技术；
- `packaging_processing`：包装、标签、加工、制造和设备技术；
- `retail_foodservice`：零售、便利店、餐饮、菜单和渠道动态；
- `japan`、`korea`、`southeast_asia`：日本、韩国和东南亚本地行业来源；
- `research_data`：研究机构、趋势报告和商业数据线索；
- `x_watch`：已确认保留的 X 弱信号账号，默认关闭。

同一个来源可以属于多个来源包，但每次运行只抓取一次。使用者可以启用或禁用来源包、覆盖其中单个来源，或按公开 Schema 添加新的 RSS、API、HTML 和查询来源。

候选池人工筛选已保留 59 个 `M` 系列来源，其中最终默认启用项由 14 天试跑确定。社交候选仅保留 6 个 X 账号作为默认关闭的观察项；FoodScope 默认来源包、示例配置和食品行业筛选结果中不包含 Reddit。Horizon 继承的通用 Reddit 适配器无需为此从核心删除。

### 4.3 采集运行层

来源的采集运行层只控制成本、频率和接入优先级，不进入内容评分：

- 核心源：每次计划任务稳定采集；
- 扩展源：轮换采集，或在某个主题、区域内容不足时补位；
- 发现源：通过关键词和聚合结果扩大覆盖面，再执行证据回链。

来源的证据等级与采集运行层是两组不同字段。核心源不因“核心”标签获得更高内容分；扩展源中的高价值事件可以排在核心源内容之前。

### 4.4 多语言发现查询与弱信号

20 组查询是可配置的主题与语言组合，不是固定网站列表。每组的查询式、市场、语种、分类提示和候选上限记录在[《一期来源与发现查询目录》](2026-07-23-foodscope-source-catalog.md)中。法规、标准和召回主要由官方证据包承担，发现查询集中补足：

- 新品、饮料和餐饮菜单创新；
- 新原料、食品添加剂、发酵、生物技术和加工工艺；
- 可持续、可回收、智能包装与标签技术；
- 健康、功能性、减糖、植物基和替代蛋白；
- 消费趋势、零售和餐饮动态；
- 品牌策略、产品组合、溢价化和本地化；
- 食品科技投融资、并购、合作、新工厂和创新中心；
- 日本、韩国和东南亚的本地市场与企业动态。

每组按英语、日语、韩语或目标市场关键词配置。查询结果进入候选池后再执行时间、来源、相关性、证据和重复性校验。

`x_watch` 不属于 20 组发现查询，默认关闭。只有在账号归属、活跃度、平台条款、官方 API 或授权方式与处理成本均通过复核后，才可小规模启用。未配置合规访问方式时只保留人工观察。

## 5. 食品情报模型与 AI 流水线

### 5.1 内容字段

统一内容对象在 Horizon `ContentItem` 基础上增加：

- 市场与国家；
- 主分类与多值标签；
- 食品品类、原料/技术、品牌/企业；
- 来源证据等级、采集运行层与原始语言；
- 原文标题、中文标题和中文摘要；
- 重要性、画像相关性、商业机会、风险和证据质量；
- 研发意义、风险信号、机会信号、建议关注动作；
- 原始出处、补充证据链接；
- 模型、提示词和分析 Schema 版本。

新品内容额外提取：

- 上市国家、上市时间、品牌、企业和产品名称；
- 食品品类、目标人群、核心原料、口味和产品形态；
- 营养或功能宣称、包装规格、售价和销售渠道；
- 新品类型：全新产品、系列扩展、配方升级、包装焕新或区域上市。

### 5.2 固定分类

主分类只能选择一个：

1. 产品创新
2. 原料与技术
3. 包装与标签
4. 消费趋势
5. 法规与标准
6. 食品安全与召回
7. 零售餐饮
8. 企业动态

“新品”属于产品创新主分类，同时通过专用来源包、标签、字段和简报画像加强，不新增含义重叠的第九个主分类。内容可同时具有多个市场、品类、原料、企业和风险标签。

### 5.3 处理步骤

1. 并发抓取全部启用来源，保存原始响应和允许保存的正文。
2. 标准化时间、URL、来源、语言和基础元数据。
3. 快速模型翻译标题与摘要，执行食品相关性判断、分类和实体抽取。
4. 规范化 URL 去重；以中文化标题、企业、产品和事件生成 7 天事件指纹；同次运行再由分析模型合并跨语言同事件。
5. 分别生成重要性、画像相关性、商业机会、风险和证据质量，不用单一总分代替这些维度。
6. 执行证据准入和赞助、新闻稿、供应商观点标记。
7. 按当前画像排序，并应用主题、地区、来源和品类的多样性软配额。
8. 对入选候选生成研发意义、潜在风险、可借鉴方向和建议关注动作。
9. 生成统一内容事实版本，再渲染各渠道格式。

所有模型输出必须通过 Pydantic Schema 校验。单条最多重试三次，仍失败则进入隔离清单且不进入简报。模型不得生成无来源的具体法规条文、日期、限量或处罚结论。

### 5.4 自动入报与反偏向

- 全流程不设置人工审批。
- 一级和二级来源通过最低分数、时间、证据与重复校验后可自动入报。
- 三级来源必须满足原始出处或双来源验证规则；四级来源必须先回链至可独立核验出处。
- 法规、标准、召回和食品安全内容必须具有官方证据链接。
- 失败、缺正文、日期不可判定、Schema 不合格或证据不足的内容进入隔离清单。
- 单一媒体不得长期占据过多条目；同一事件无论被多少媒体报道，只生成一个事件卡片。
- 配额是软目标；候选不足时不得用低质量内容凑数。
- 赞助稿、供应商自述和新闻稿必须显式标记并降低证据权重。
- 每份简报保留少量探索位，用于纳入当前画像之外但可能重要的新信号。
- 高风险和严重事件进入顶部风险提醒，不受普通栏目配额限制，也不挤占市场、新品或研发正文配额。
- 每条入报内容保存评分理由、证据链接和画像选择理由，便于开源使用者检查和修改。
- 简报明确标注 AI 生成与“仅供行业研究参考，不构成法律或合规意见”。

## 6. 简报画像与分发

### 6.1 内置画像

内置五种画像：

- `balanced`：综合情报；首次运行默认值，商业与技术内容原则上不少于 70%；
- `market`：消费趋势、零售餐饮、企业动态、品牌策略和投融资；
- `new_products`：新品、创新点、目标人群、原料宣称、包装、价格与渠道策略；
- `rd`：新品研发、配方、原料、加工和包装技术；
- `compliance`：法规、标准、标签、召回和食品安全。

画像只调整主题权重、排序和栏目配额，不改变来源证据等级、事实核验或风险准入规则。使用者可以复制内置画像，调整主题、地区、品类、来源和栏目限制，并保存为自定义画像。

一期每次运行启用一个画像，不建设用户账号和多订阅管理。内容模型保留未来从同一候选池生成多份画像简报的能力。

### 6.2 简报结构

所有画像使用统一外层结构：

1. 标题、画像、日期、覆盖时间窗和运行统计；
2. 重大风险提醒；
3. 今日必读，最多 5 条；
4. 按画像排序的主题章节；
5. 今日启示与值得持续观察的信号；
6. 来源与 AI 声明。

综合情报版覆盖八个主分类；其他画像优先展示与画像相关的章节，不强制输出空章节。每条情报输出中文标题、原文标题、三句摘要、发生了什么、为何值得中国食品企业关注、可借鉴方向、潜在风险、建议动作、市场/分类/标签、证据等级和原文链接。

最终入报通常为 15–25 条。综合情报版中产品创新、原料与技术、包装与标签、消费趋势、零售餐饮和企业动态六类商业/技术内容原则上不少于 70%；法规与标准、食品安全与召回普通内容原则上不超过 30%。高风险或严重事件通过顶部风险提醒呈现，不受该比例限制。

### 6.3 渠道

- Markdown：完整权威归档。
- HTML：由同一事实版本渲染，内联样式，供邮件和公众号复用。
- 邮件：使用现有 SMTP/IMAP 能力发送完整日报并支持退订。
- 飞书：复用并扩展 Horizon Card JSON 2.0 折叠卡片；超长时发送概览加分类卡片。
- 微信公众号：通过公众号 API 写入草稿箱，不在一期自动执行群发；使用配置的永久封面素材，正文保留原文链接和声明。
- MCP：沿用 Horizon 本地 stdio MCP，扩展食品行业阶段字段、运行列表、隔离清单和最新简报资源。通用 Agent 可校验配置、触发流水线、读取各阶段和简报，但不能修改配置、删除产物或直接群发。

各渠道独立重试并记录结果。某个渠道失败不会回滚已生成简报或阻止其他渠道发送。

## 7. 可靠性与安全

- HTTP 抓取设置域名级并发、超时、指数退避、User-Agent 和频率限制。
- 遵守 robots、站点条款和版权边界；简报只保存必要摘要与证据链接，不转载受版权保护的完整文章。
- X 只通过平台明确允许的官方 API 或授权方式接入，不绕过登录、速率限制或付费权限；默认只保存帖子 ID、账号 ID、URL、时间和短线索，并同步处理删除、编辑和失效状态。
- URL 访问执行 SSRF 防护，拒绝私网、环回、文件协议和重定向到受限地址。
- 日志不得输出 API key、Webhook、邮箱密码或公众号凭证。
- 定时任务设置运行锁，避免同一时间窗重复执行；手动补跑必须显式指定是否重新分发。
- 运行完成时输出各来源成功率、抓取数、有效候选数、去重数、入报数、隔离数、模型 token 与成本、分渠道结果和总耗时。

## 8. 测试与验收

- Horizon 回归测试：保留并运行上游核心、CLI、配置、AI 路由和分发测试。
- 单元测试：配置、来源解析、时间标准化、URL 规范化、跨日指纹、跨语言事件去重、分类配额、证据准入、画像排序、Schema 校验、模板渲染和秘密脱敏。
- 契约测试：每个专用官方来源和非通用媒体适配器保存脱敏 fixture，验证页面、API 或附件格式变化能被检测。
- AI 测试：使用固定中英日韩样本和模拟客户端，覆盖分类、实体、新品字段、五维评分、正常 JSON、格式错误、超时、重试和隔离。
- 端到端测试：以本地 fixture 完成全阶段运行，验证五种画像及 Markdown、HTML、邮件、飞书、微信草稿请求和 MCP 资源使用同一事实版本。
- 故障测试：单源失败、单条解析失败、快速模型失败、分析模型失败、单个分发渠道失败、重复调度和阶段恢复。
- 发布验收：连续 14 天试运行，核对定时完成率、相关率、重复率、原文链接有效率、商业信息占比、画像多样性、渠道成功率和模型成本。
- 来源验收：分别核对抓取成功率、有效独家信号数、商业/技术内容占比、跨源重复率、赞助内容比例、付费墙与访问限制；不达标时从保留候选中启用替补。

测试 fixture 不得包含真实密钥、个人数据或不必要的受版权保护全文。

## 9. 开源发行与贡献

- 仓库提供可直接复制的 `.env.example`、`data/config.example.json` 和五种内置画像。
- 文档公开来源包 Schema、自定义来源、画像权重、评分理由、证据规则、模型配置和各渠道部署方式。
- 贡献指南说明如何增加国家、媒体、来源包、适配器、食品标签和简报模板，以及相应测试要求。
- 默认配置能够在仅提供 AI 密钥且至少启用一个输出方式时完成本地简报生成。
- 项目不内置第三方文章全文、付费内容、真实订阅者数据或任何服务密钥。

## 10. 一期边界与后续

一期不建设长期内容数据库、公开资讯站、站内搜索、用户画像、收藏、个性化订阅后台、可视化权重设置、多租户或付费。使用者通过 JSON 配置和初始化向导选择来源包、简报画像、运行时间和分发渠道。

后续可在保持配置文件为唯一权威来源的前提下增加可视化设置，让使用者调整主题、地区、品类、来源和栏目权重；也可从同一候选池生成多份画像简报。若简报质量和使用频率得到验证，再将同一内容模型迁移到持久化数据库和产品网站。第一期文件产物与版本字段必须保证未来可导入。
